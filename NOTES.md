## 1. Главное решение: стоимость считается на чтении

Ставка и стоимость **не хранятся** в документе записи табеля. Запись хранит только
сотрудника, проект, дату и часы; ставка на дату записи и стоимость вычисляются в конвейере
агрегации в момент чтения.

**Почему так.** Ставки можно менять задним числом — это прямо написано в задании, и
приёмочный сценарий 8 требует, чтобы после смены ставки отчёт за март пересчитался.
При денормализованной стоимости это означает, что любое изменение истории ставок должно
запускать пересчёт всех затронутых записей. Пока пересчёт не прошёл (или если ставку
поправили мимо приложения — миграцией, скриптом, руками в mongosh), отчёт врёт, и врёт молча.
Расчёт на чтении даёт единственный источник правды: история ставок.

**Чем платим.** В конвейере есть `$lookup` в `employees` на каждую запись отобранного
месяца. Коллекция сотрудников маленькая, join идёт по `_id` (уникальный индекс), документы
почти наверняка сидят в кэше — но это всё равно дороже, чем чтение готового числа из поля.

**Как масштабировать, если этого станет мало** (тот самый вопрос «а как бы вы это масштабировали»):

1. Денормализовать `rate` и `amount` в запись при сохранении, а изменение истории ставок
   поставить фоновой задачей (у вас для этого уже есть Hangfire), которая пересчитывает
   записи затронутого сотрудника с даты изменения. Тогда отчёт становится
   `$match` + `$group` без единого `$lookup`. Цена — окно рассогласования и обязательное
   требование менять ставки только через приложение.
2. Сгруппировать до `$lookup`: сначала `$group` по `(проект, сотрудник, дата)`, и только
   потом подтягивать сотрудника. Число документов, доходящих до join, падает на порядки.
   Я этого не сделал сознательно: тогда округление до копеек происходит не на записи, а на
   группе, и в редких случаях (нечётное число получасов × ставка с копейками) итог отчёта
   разошёлся бы с суммой строк на экране табеля на копейку. Требование «стоимость записи =
   часы × ставка, округление до копеек» важнее экономии на join.
3. Предагрегированные помесячные итоги по проектам, обновляемые на запись
   (или через change streams — они у вас уже используются). Это уже про отчёты за год
   и дашборды, а не про отчёт за месяц.

## 2. Как устроены конвейеры

Все стадии собраны в одном месте — `Infrastructure/TimesheetPipelines.cs`, — потому что
список записей и отчёт **обязаны** считать стоимость абсолютно одинаково.

**Ставка на дату** (`AddEffectiveRate`) — `$reduce` по массиву ставок: берётся та, у которой
`from ≤ date` и `from` максимальна. Порядок элементов массива не используется: сортировать
массив при записи можно, но полагаться на это в расчёте нельзя. Это точный аналог
`RateSchedule.Effective` в C#, и оба варианта покрыты одними и теми же кейсами в тестах.

**Список записей** — `$match` → `$sort` → `$skip` → `$limit` → и только потом `$lookup`
справочников и расчёт. Порядок именно такой: подтягивать сотрудников и проекты для всего
месяца, чтобы показать двадцать строк, незачем.

**Итоги списка** — отдельный конвейер по тому же `$match` с `$group`. Итоги считаются по
**всему отфильтрованному списку**, а не по странице, поэтому обойтись первым конвейером
нельзя. Заодно этот же `$group` отдаёт общее количество записей — отдельный `count` не нужен.

**Отчёт** — один конвейер: `$match` месяца → ставка → стоимость → `$group` по проекту →
`$facet` на строки и итог. Проект подтягивается **внутри** `$facet`, то есть уже после
группировки: по одному документу на проект вместо одного на каждую запись табеля. Процент
освоения, признак перерасхода (>100 %) и признак риска (>80 %) считает база, C# только
раскладывает результат в DTO.

**Отметка переработки** — свойство дня, а не записи: чтобы её посчитать, нужен итог по всем
проектам сотрудника за эту дату. Внутри строки списка это не считается, поэтому после
выборки страницы идёт второй маленький запрос: `$group` по `(сотрудник, дата)` для тех пар,
что попали на страницу. Он ложится на индекс `employee_date`.

## 3. Индексы и почему именно они

Создаются явно при старте (`MongoIndexes.EnsureAsync`, `CreateMany` идемпотентен).

| Коллекция | Индекс | Зачем |
|-----------|--------|-------|
| `time_entries` | `{ date: 1, employeeId: 1, projectId: 1 }` | Основной. Отбор месяца — это диапазон по `date`; сортировка списка тоже по `date`, то есть берётся прямо из индекса, без in-memory sort. Хвост из `employeeId`/`projectId` позволяет дофильтровать выборку месяца, не заглядывая в документы. |
| `time_entries` | `{ employeeId: 1, date: 1 }` | Проверка лимита 24 часа за день и подсчёт часов по дням: два равенства подряд — самый выгодный для индекса случай. По основному индексу этот запрос шёл бы диапазоном по дате с фильтрацией по сотруднику. |
| `time_entries` | `{ projectId: 1, date: 1 }` | Фильтр «месяц + проект»: равенство по проекту селективнее, чем диапазон по месяцу, поэтому оно должно стоять первым. |
| `projects` | `{ code: 1 }`, unique | Шифр проекта уникален по условию — пусть это гарантирует база, а не только код. |
| `closed_periods` | `{ year: 1, month: 1 }`, unique | Один документ на месяц; уникальность защищает от гонки при одновременном закрытии периода. |
| `employees` | `{ fullName: 1 }` | Справочник отдаётся отсортированным; без индекса это сортировка в памяти на каждый запрос. |

Составные индексы упорядочены по правилу ESR (equality → sort → range).
Индекса под `$lookup` заводить не нужно: join идёт по `_id`, он уникален по определению.

## 4. Деньги: decimal и режим округления

`decimal` во всей цепочке, в MongoDB — `Decimal128`. В C#-драйвере `decimal` по умолчанию
сериализуется **строкой**, поэтому в `MongoSetup` явно зарегистрирован
`DecimalSerializer(BsonType.Decimal128)`: строку нельзя ни просуммировать в `$group`, ни
сравнить в `$gt`. Часы — тоже `decimal`, чтобы `часы × ставка` не выпадало в double.

Округление — **до копеек, к чётному** (`MidpointRounding.ToEven`). Это не «дефолт .NET по
инерции», а требование согласованности: оператор `$round` в MongoDB округляет именно так,
а стоимость считается в двух местах — в списке записей и в отчёте. Возьми я в C#
`AwayFromZero`, значения бы иногда расходились на копейку с тем, что посчитала база.

Если бухгалтерии нужен именно half-up — менять надо **оба** места: `Money.Round` и выражение
в конвейере (в `$round` режима нет, half-up эмулируется через `$floor` от `x·100 + 0,5`).
Это первый вопрос, который я бы задал по деньгам.

## 5. Даты

Дата записи табеля — это календарная дата без времени и без зоны. Наружу она ходит как
`DateOnly` (`"2026-03-05"`), внутри и в базе — `DateTime` с `Kind = Utc` и нулевым временем.
Единственная точка преобразования — `Domain/Dates.cs`.

BSON-даты всегда UTC, поэтому в `MongoSetup` зарегистрирован
`DateTimeSerializer(DateTimeKind.Utc)`: иначе из базы приезжали бы `Unspecified`, которые
при первом же `ToUniversalTime()` молча уехали бы на часовой пояс сервера. Границы месяца —
полуинтервал `[первое число, первое число следующего месяца)`: это ложится на индекс,
в отличие от `date.Year == y && date.Month == m`.

## 6. Конкурентность

**Оптимистичная блокировка** сделана через поле `version`. Изменение идёт как
`UpdateOne({ _id, version }, { $set: …, $inc: { version: 1 } })`. `MatchedCount == 0`
означает, что запись либо удалили (404), либо её версия уже другая (409
`CONCURRENT_MODIFICATION` с указанием обеих версий). Удаление тоже принимает `version` —
необязательный параметр, но интерфейс его всегда передаёт.

На фронтенде для этого пришлось выключить `refetchOnWindowFocus` у react-query: иначе
вторая вкладка при возврате фокуса получала бы свежую версию записи, и приёмочный
сценарий 7 было бы не воспроизвести.

**Что осталось незакрытым и я это знаю.** Проверка лимита «24 часа за день» — это
read-then-write: между подсчётом часов и вставкой записи другой запрос может вставить свою.
Два одновременных сохранения по 20 часов на один день пройдут оба. Варианты решения:
транзакция (реплика-сет обязателен) или документ-агрегат «часы сотрудника за день» с
атомарным `$inc` и уникальным индексом. Для табеля, который заполняет сам сотрудник,
вероятность гонки исчезающе мала, а цена решения заметна, поэтому в объём 6–8 часов я это
не включил.

## 7. Ошибки: 400 против 409

Разделение простое и проходит через весь код:

* **400** — проблема в самом запросе: формат, обязательность, кратность, диапазон.
  Это `Validation/`, там нет ни одного обращения к базе.
* **409** — запрос корректен, но конфликтует с текущим состоянием данных: закрытый период,
  лимит часов за день, отсутствие ставки на дату, дата вне периода проекта, чужие изменения.
  Это `Domain/TimeEntryRules.cs`, куда сервис приносит уже загруженные данные.
* **404** — объекта нет.
* **500** — только настоящие сбои, и наружу из них не уходит текст исключения.

Единственное место, где исключение превращается в HTTP-ответ, — `ErrorHandlingMiddleware`.
Контроллеры не ловят ничего. Формат ответа одинаков везде, включая ошибки привязки модели
(`InvalidModelStateResponseFactory` переопределён, чтобы не было двух разных форматов ошибок).

Мелочь, которая на самом деле не мелочь: middleware **не вызывает** `Response.Clear()` —
он снёс бы заголовки CORS, и браузер не смог бы прочитать текст ошибки. Ровно тот случай,
когда «ошибки видит пользователь» ломается на ровном месте.

## 8. Выбор инструментов

**Без MediatR.** Задание разрешает «MediatR или обычные сервисы». Здесь четыре сценария
записи и три чтения — конвейер команд не окупается: он добавляет по два типа на операцию и
слой косвенности между контроллером и логикой. Сервисы с явными зависимостями читаются
прямее. В вашем проекте MediatR уже стоит, и перенос кода на него механический: тело метода
сервиса становится телом `Handle`.

**Без FluentValidation.** По той же причине: валидаторы здесь — это три десятка строк
понятного кода, который собирает все ошибки формы за один проход и возвращает их с полями.
Отдельная библиотека в проект на 6–8 часов не окупается, а разделение «формат — отдельно,
бизнес-правила — отдельно» от неё не зависит.

**react-query.** Данные экрана — это серверное состояние: его надо загрузить, показать
устаревшее во время обновления, инвалидировать после мутации и не устроить гонку ответов
при быстрой смене фильтров. react-query закрывает всё это из коробки, а собственного
клиентского состояния на этих двух экранах почти нет — держать ради него mobx-state-tree
не за что. Если экран разрастётся (черновики форм, массовое редактирование, оффлайн),
локальное состояние уедет в стор, а react-query останется отвечать за загрузку.

**Компонентной библиотеки нет** — дизайн не оценивается, свой CSS на два экрана короче,
чем настройка чужой темы.

**.NET 8 вместо .NET 5.** Из синтаксиса используются только возможности C# 10 и ниже
(file-scoped namespaces, records, target-typed `new`). Перенос на .NET 5 — это смена
`TargetFramework`, возврат блочных namespace и `DateOnly` → `DateTime` в контрактах.

## 9. Принятые допущения

Задание оставляет несколько мест недосказанными. Что я решил и почему:

1. **Переработка — свойство дня, а не записи.** Если за 06.03 у сотрудника 20 часов на трёх
   проектах, помечены все три записи этого дня, и в подсказке показан итог за день.
2. **Лимит 24 часа считается по всем записям дня**, включая те, что лежат в закрытых
   периодах: физически в сутках 24 часа независимо от того, закрыт месяц или нет.
3. **Запись нельзя ни вынести из закрытого месяца, ни занести в него.** При изменении даты
   проверяются оба месяца — старый и новый.
4. **Признак риска (>80 %) и признак перерасхода (>100 %) не исключают друг друга.**
   140 % — это и то, и другое; в интерфейсе перерасход имеет приоритет.
5. **Сравнения границ строгие**: ровно 12 часов — ещё не переработка, ровно 24 — ещё не
   превышение, ровно 100 % — ещё не перерасход. Так написано в задании («больше 12»,
   «не больше 24», «больше 100 %»).
6. **Дата начала и окончания проекта включаются в период.**
7. **Версия обязательна при изменении** и необязательна при удалении.
8. **Повторное закрытие уже закрытого месяца — не ошибка**, операция идемпотентна.
9. **Ставку удалили задним числом, и у записи не стало ставки** — запись не исчезает из
   отчёта: она попадает туда со стоимостью 0 и пустой ставкой. Тихо терять часы хуже,
   чем показать аномалию.
10. **Аутентификации нет**, но служебные поля «кто создал/изменил» заполняются из заголовка
    `X-User` — чтобы было видно, куда встроится настоящая аутентификация.
11. **`pageSize` ограничен сверху 200** — иначе `pageSize=100000` превращает пагинацию
    обратно в выгрузку всего месяца.
12. **Метод правки ставок** (`PUT /api/employees/{id}/rates`) в задании не описан; добавлен,
    чтобы приёмочный сценарий 8 проверялся через API, а не руками в базе.

## 10. Вопросы, которые я бы задал

Ровно те места, где я принял решение сам и где оно может разойтись с вашим:

1. Округление денег — к чётному или half-up (арифметическое)? Как считает ваша бухгалтерия?
2. Переработка помечает день целиком или конкретную запись, которая вывела день за 12 часов?
3. Что делают с записями, когда ставку меняют задним числом: пересчитывают хранимую
   стоимость фоновой задачей или считают на лету? Второй вариант я выбрал, но у вас
   уже есть Hangfire — возможно, у вас принято иначе.
4. Разрешено ли редактированием переносить запись из закрытого месяца в открытый?
5. Признак риска — «больше 80 %» или «от 80 до 100 %» (то есть перерасход его выключает)?
6. Нужна ли история изменений записи (кто, когда, что поменял), или достаточно полей
   «кем создана / кем изменена»? Задание упоминает «служебные поля на ваше усмотрение».
7. Кто имеет право закрывать период — при появлении ролей это первое место, куда они лягут.
8. Должен ли отчёт показывать проекты, по которым за месяц не было трудозатрат
   (сейчас — нет, как написано в задании)?

## 11. Что осознанно не сделано

* **Аутентификация, роли, права** — исключены заданием.
* **Интеграционные тесты с реальной MongoDB.** Конвейеры проверены на приёмочных данных
  вручную, а арифметика продублирована юнит-тестами (`AcceptanceReportTests` считает те же
  цифры доменным кодом). Полноценно это закрывается тестами на `Testcontainers` — см. ниже.
* **CI/CD, метрики, трассировка.**
* **Виртуализация таблицы, сортировка по колонкам, сохранение фильтров в URL.**
* **Локализация** — интерфейс и тексты ошибок только на русском.
* **Транзакция вокруг проверки лимита часов** — см. раздел 6.

## 12. Что сделал бы, будь времени вдвое больше

1. **Интеграционные тесты на Testcontainers**: поднять mongo:7, залить сид, прогнать все
   восемь приёмочных сценариев через HTTP. Это единственный способ проверить сами конвейеры,
   а не только арифметику вокруг них — сейчас это главный пробел в тестах.
2. **Транзакцию или документ-агрегат для лимита часов** и заодно тест на гонку.
3. **Денормализацию `rate`/`amount` с пересчётом на Hangfire** — как второй режим, с явным
   переключателем, чтобы можно было сравнить производительность на реальном объёме.
4. **`explain()` на всех запросах в тестах**: проверять, что план — `IXSCAN`, а не `COLLSCAN`,
   и что новый индекс не появился «на всякий случай». Регрессии по производительности
   ловятся так же, как регрессии по логике.
5. **История изменений записи** отдельной коллекцией — для табеля это обычно оказывается
   нужно сразу после первого спора «я это не менял».
6. **Массовый ввод в интерфейсе**: сетка «сотрудник × день» с вводом часов прямо в ячейку.
   Табель за месяц по одной записи через модальное окно — это долго, а именно этим
   пользователи занимаются каждый день.
