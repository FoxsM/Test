## 🔴 Критичные

### 1. Ставка выбирается неправильно — отчёт врёт про деньги

```csharp
var rate = employee.Rates.FirstOrDefault().Value;
```

**Суть.** Берётся *первая ставка из массива*, а не та, что действовала на дату записи.
Порядок элементов массива в BSON — это порядок, в котором их когда-то записали; никакой
сортировки по дате никто не гарантирует. Даже если массив отсортирован, «первая» — это
самая старая ставка, а не актуальная.

**Чем грозит в продакшене.** Это худший вид ошибки: система не падает, отчёт строится,
цифры выглядят правдоподобно. Стоимость работ по всем проектам занижена (или завышена)
на разницу ставок. Ошибку заметят через квартал, когда сойдутся с бухгалтерией — и после
этого перестанут доверять всем отчётам системы. Отдельно: `FirstOrDefault()` на пустом
списке ставок вернёт `null`, и `.Value` даст `NullReferenceException` → 500.

**Как чинить.** Правило «ставка, действовавшая на дату» — доменное, его место в отдельной
функции, которую переиспользуют и отчёт, и запись табеля:

```csharp
rates.Where(r => r.From <= date).OrderByDescending(r => r.From).FirstOrDefault()
```

В агрегации это `$reduce` по массиву ставок с выбором максимальной `from`, не превышающей
дату записи (см. `AddEffectiveRate` в части 2 и `FIX 2` в исправленном файле).
Если ставки на дату нет — это не «ноль рублей», а отказ с внятным текстом.

### 2. Вся коллекция выгружается в память

```csharp
var entries = await _db.GetCollection<TimeEntry>("time_entries")
    .Find(FilterDefinition<TimeEntry>.Empty)
    .ToListAsync();

var monthEntries = entries.Where(e => e.Date.Year == request.Year && ...)
```

**Суть.** Из базы читается **всё**, фильтрация по месяцу делается в C#.

**Чем грозит.** На нескольких миллионах записей это сотни мегабайт в LOH на каждый запрос
отчёта: рост GC pause, `OutOfMemoryException`, таймауты. Хуже всего, что два человека,
открывшие отчёт одновременно, положат процесс. На тестовой базе в тысячу записей проблема
не воспроизводится вообще — поэтому она и доезжает до прода.

**Как чинить.** Отбор месяца — `$match` по полуинтервалу `[начало месяца, начало следующего)`
с индексом по `date`; группировка — `$group` на стороне MongoDB. В C# должны приезжать
уже готовые строки отчёта (по одной на проект), а не записи табеля.

### 3. `useEffect` без массива зависимостей — бесконечный цикл

```tsx
useEffect(() => {
    load();
});
```

**Суть.** Эффект без второго аргумента выполняется **после каждого рендера**. `load()`
делает `setEntries` → рендер → эффект → `load()` → … Цикл разрывается только тем, что
запросы идут по сети.

**Чем грозит.** Вкладка непрерывно долбит `/api/time-entries` — десятки запросов в секунду
с каждого открытого экрана. Это и счёт за трафик, и нагрузка на базу, и «непонятные
всплески» в мониторинге, которые долго ищут. У пользователя — греющийся ноутбук и
подвисающий интерфейс.

**Как чинить.** Указать зависимости (`[year, month, employeeId, page]`) и обернуть `load`
в `useCallback` — или, что правильнее, вынести загрузку в `react-query`/стор, где
ключ запроса и есть список зависимостей.

---

### 4. `double` для денег

```csharp
public double Amount { get; set; }
public double Budget { get; set; }
var amount = Math.Round(entry.Hours * rate, 2);
```

**Суть.** `double` — двоичная дробь, десятичные копейки в ней непредставимы точно.
`Math.Round` округляет уже испорченное значение и ошибку не устраняет: она накапливается
на суммировании тысяч записей.

**Чем грозит.** Итог отчёта не сходится с суммой строк на копейки. Для системы, из которой
считают зарплату и рентабельность, это блокирующая проблема: расхождение придётся
объяснять, а «плавающая ошибка» невоспроизводима и потому неисправима задним числом.
Плюс `double` спокойно даёт `Infinity` и `NaN` (см. проблему 8), а `decimal` в тех же
условиях бросит исключение, которое видно сразу.

**Как чинить.** `decimal` во всей цепочке: ставка, часы, стоимость, бюджет. В MongoDB —
`Decimal128` (в C#-драйвере `decimal` по умолчанию сериализуется **строкой**, поэтому нужен
явный `DecimalSerializer(BsonType.Decimal128)`, иначе суммирование в `$group` работать не будет).

## 🟠 Серьёзные

### 5. `.Result` внутри async-метода

```csharp
var employee = _db.GetCollection<Employee>("employees")
    .Find(e => e.Id == entry.EmployeeId)
    .FirstOrDefaultAsync().Result;
```

Блокирующее ожидание асинхронной операции. В ASP.NET Core классического дедлока
(как в старом ASP.NET с `SynchronizationContext`) не будет, но поток пула стоит и ждёт
сеть — вместо того чтобы обслуживать другие запросы. Под нагрузкой это thread pool
starvation: время ответа растёт лавинообразно на всех эндпоинтах, а не только на отчёте.
Плюс исключения приезжают завёрнутыми в `AggregateException`, и в логах вместо причины
видно обёртку. Чинится `await` — а в данном случае этот запрос вообще исчезает (проблема 6).

### 6. N+1 запросов

Сотрудник запрашивается **в цикле для каждой записи**, проект — при каждом первом
появлении. 100 000 записей → 100 000 round trip'ов к базе. Даже при 1 мс на запрос это
100 секунд. И это при том, что сотрудников в компании двести. Чинится `$lookup` в конвейере
или предварительной загрузкой словаря сотрудников (их мало), если бы расчёт оставался в C#.

### 7. Нет проверок на null

`employee.Rates`, `project.Id`, `project.Name` разыменовываются без проверки. Запись, у
которой удалили сотрудника или проект (а в живой базе за годы такие всегда есть), даёт
`NullReferenceException` → 500 на весь отчёт. Один битый документ ломает страницу целиком.
Чинится `preserveNullAndEmptyArrays` в `$unwind` + `$ifNull` для подстановки заглушек:
запись должна попасть в отчёт с пометкой, а не уронить его.

### 8. Деление на нулевой бюджет

```csharp
row.Percent = Math.Round(row.Amount / row.Budget * 100, 2);
```

У проекта без бюджета (`Budget = 0`) получается `Infinity`, а при `Amount = 0` — `NaN`.
`Math.Round(NaN)` — это `NaN`. `System.Text.Json` по умолчанию **бросает исключение** при
сериализации `NaN`/`Infinity` → 500 на ровном месте. С `decimal` в этом месте было бы
`DivideByZeroException` — тоже 500, но хотя бы очевидное. Чинится явной проверкой:
процент освоения при отсутствующем бюджете — это `null`, а не число.

### 9. Мутация состояния вместо нового массива

```tsx
entries.push(body);
setEntries(entries);
```

`setEntries` получает **ту же ссылку**, React сравнивает через `Object.is`, изменений не
видит и не перерисовывает таблицу. Пользователь нажимает «Добавить», запись сохраняется на
сервере, но на экране не появляется — классическое «кнопка не работает, нажму ещё раз»,
которое кончается дублями. А если рендер всё же случится по другой причине, в таблицу
попадёт сырой `body` — без `id`, без `amount`, с датой в другом формате — и следующий же
рендер упадёт на `entry.amount.toFixed(2)`. Чинится перезагрузкой списка с сервера:
стоимость, переработку и версию считает бэкенд, клиент их не выдумывает.

### 10. Нет обработки ошибок fetch

`fetch` **не бросает** на 4xx/5xx — он спокойно резолвится. Ни `response.ok`, ни `try/catch`
в коде нет. Сервер ответил 409 «период закрыт» — пользователь видит «Сохранено». Все
бизнес-правила, которые так старательно проверяет бэкенд, для пользователя не существуют.
Чинится общим клиентом, который проверяет статус и бросает типизированную ошибку с кодом
и текстом, а компонент её показывает.

### 11. Сообщение об успехе выдаётся до проверки результата

Прямое следствие проблемы 10: `alert("Сохранено")` вызывается безусловно. Отдельно стоит
заменить `alert` на нормальное уведомление — модальный `alert` блокирует поток и в
проектном интерфейсе смотрится инородно.

### 12. Дата уходит на сервер в локализованном виде

```tsx
date: new Date(date).toLocaleDateString(),
```

`toLocaleDateString()` даёт `05.03.2026` в русской локали и `3/5/2026` в американской —
результат зависит от настроек **браузера пользователя**. Сервер такую строку либо не
разберёт (400 на пустом месте), либо разберёт неправильно и запишет 3 мая вместо 5 марта.
Плюс `new Date("что угодно")` даёт `Invalid Date` без единой жалобы. Между клиентом и
сервером дата должна ходить в ISO (`yyyy-MM-dd`) — `input[type=date]` отдаёт ровно его.

## 🟡 Средние

### 13. `CancellationToken` не доходит до драйвера

Параметр `token` объявлен и не используется ни в одном вызове. Пользователь закрыл вкладку
или ушёл со страницы — база продолжает считать отчёт до конца. На тяжёлых отчётах это
означает, что нетерпеливый пользователь, обновивший страницу пять раз, оставит после себя
пять параллельных запросов.

### 14. Фильтр по `Date.Year` / `Date.Month`

Даже если бы фильтрация выполнялась в базе, `e.Date.Year == year && e.Date.Month == month`
не ложится на индекс: это вычисление над полем, а не диапазон. Нужен полуинтервал
`[from, to)`. Второе: границы месяца надо строить в UTC — в BSON даты всегда UTC, и если
сервер стоит в UTC+3, `new DateTime(y, m, 1)` с `Kind = Unspecified` сдвинет границу
на три часа, и записи первого/последнего дня месяца уедут в соседний период.

### 15–16. Деньги и итоги считаются на клиенте

```tsx
total = total + parseFloat(filtered[i].amount);
```

Два источника правды по деньгам: сервер посчитал одно, клиент складывает другое
(`parseFloat` — это тот же `double`). При появлении пагинации итог станет ещё и неверным по
смыслу: он посчитается по видимым строкам, а не по всему фильтру. Итоги должен считать и
отдавать бэкенд.

### 17. `entry.amount.toFixed(2)` без проверки

Одна запись без `amount` (а после проблемы 9 она там появится) — и весь экран падает с
`TypeError: Cannot read properties of undefined`. React размонтирует поддерево, пользователь
видит пустую страницу. Форматирование должно быть устойчиво к `null`.

### 18. `any[]` вместо типов

Проект на TypeScript, но у экрана нет ни одного типа ответа API. Компилятор не поймает ни
переименование поля на бэкенде, ни опечатку в `entry.projectName`. Именно из-за этого
проблемы 17 и 12 вообще стали возможны.

### 19. Гонка ответов

Быстрая смена месяца или сотрудника отправляет несколько запросов; какой ответ придёт
последним — тот и покажется, независимо от того, какой был запрошен последним. Лечится
`AbortController` (или ключом запроса в react-query, где это встроено).

### 20. `loading` не сбрасывается при ошибке

`setLoading(false)` стоит после `await` без `try/finally`. Любая ошибка сети — и «Загрузка…»
остаётся на экране навсегда.

### 21. `key={index}`

Индекс как ключ ломает согласование при удалении и вставке в середину: React переиспользует
DOM-узлы не тех строк. С инпутами внутри строки это уже реальные баги («удалил одну — а
изменилась другая»). Ключ должен быть `entry.id`.

## ⚪ Косметика

### 22. `==` вместо `===`

`e.employeeId == employeeId` — здесь оба операнда строки и всё сработает, но привычка
опасная: `"" == 0` истинно, а именно `""` означает «все сотрудники».

### 23. Мелочи интерфейса

Нет `<thead>` — колонки не подписаны, и «8» в третьей колонке можно прочитать как что
угодно. Удаление без подтверждения. Инлайн-стили вместо классов — в проекте с Blueprint.js
это разнобой. Форма не очищается после сохранения. Поле «Проект» — это текстовый ввод
идентификатора, хотя рядом уже есть готовый `select` по сотрудникам.

### 24. `Overspent` считается по округлённому проценту

`row.Percent > 100` после `Math.Round(..., 2)`: перерасход в 100,004 % округлится до 100,00
и флаг не поднимется. Пограничный случай, но правильнее сравнивать суммы (`amount > budget`),
а процент оставить для отображения.

## Что я изменил бы в структуре, а не в отдельных строках

**1. Отчёт — это работа базы, а не обработчика.**
Сейчас обработчик — это ETL: он читает сырые документы, join'ит их вручную, считает
арифметику и группирует. Всё это MongoDB делает одним конвейером. Обработчик должен
собрать конвейер, отправить его и отобразить результат в DTO.

**2. Доменные правила вынести из обработчика.**
«Ставка, действовавшая на дату» — это правило предметной области, и оно нужно **минимум в
двух местах**: при расчёте отчёта и при создании записи табеля. Пока оно живёт строкой
внутри `foreach`, второе место неизбежно реализует его иначе — и цифры на двух экранах
разойдутся. Правило должно быть отдельной чистой функцией с юнит-тестами
(в части 2 это `RateSchedule`, продублированный выражением `$reduce`, и общий тест на обе
реализации).

**3. Разделить слои: домен, доступ к данным, приложение, контракты.**
Сейчас в одном файле лежат: DTO ответа, класс запроса, обработчик, доступ к коллекциям по
строковым именам и четыре доменные сущности. Имена коллекций (`"time_entries"`) разбросаны
по коду — опечатка в строке даёт пустой отчёт вместо ошибки компиляции. Нужен контекст
(или репозитории), который знает про коллекции, домен, который не знает про Mongo, и DTO,
которые не совпадают с сущностями.

**4. Доменная модель не должна уходить наружу.**
`ProjectReportRow` одновременно и результат агрегации, и контракт API. Любое изменение
формы ответа тянет за собой изменение расчёта, и наоборот. Между ними нужен явный маппинг.

**5. Ошибки — в одном месте.**
В обработчике нет ни одной проверки, а значит любое нарушение (нет ставки, нет проекта,
кривой месяц) превращается в 500 с текстом исключения. Нужны типизированные исключения
бизнес-правил и одно middleware, которое переводит их в 400/409 с машиночитаемым кодом.

**6. Экран «Табель» — это три ответственности в одном компоненте.**
Загрузка данных, фильтры/пагинация и форма добавления. Разносится на: хук данных
(`react-query` или стор), компонент таблицы, компонент формы. Плюс один API-клиент, в
котором живут заголовки, разбор ошибок и типы ответов, — тогда обработка ошибок появляется
сразу везде, а не копируется в каждый `fetch`.

**7. Тестируемость.**
В текущем виде в обоих файлах нельзя проверить юнит-тестом ничего: вся логика склеена с
инфраструктурой. После выноса правил в чистые функции появляются тесты на выбор ставки,
лимит часов, границы периода и округление — те самые, что требуются во второй части.

## Что исправлено прямо в коде

| Файл | Что сделано |
|------|-------------|
| `part1/TimesheetReportHandler.fixed.cs` | Расчёт целиком перенесён в агрегацию MongoDB: `$match` по диапазону дат, `$lookup` вместо N+1, `$reduce` для ставки на дату записи, `$round` до копеек, `$group` по проекту, `$facet` для итоговой строки. Деньги переведены на `decimal`, добавлены проверки на null и на нулевой бюджет, проброшен `CancellationToken`, убран `.Result`. |

в части 2.
